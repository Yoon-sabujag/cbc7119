## 4. staging 작업 요청 (사용자 결정)

### 4-1. 업로드 가드 강화 (최우선)
`handleMenuUpload` 가드(현 413–442행)에 **밀림/섞임 서명 탐지** 추가:
- 후보 규칙: ① 중식 대표메뉴 요일정렬이 석식 대비 어긋남 ② 특정 평일 열 중식 결측인데 인접 열로 값 이동
  ③ 구분자 `' / '` 감지 = 옛 파서 산출 경고(신 번들이면 개행이어야).
- **한계 (반드시 병기):** 밀림 원인이 옛 파서 캐시면 **가드는 최신 번들에만 존재 → 옛 캐시 업로드는 우회**.
  따라서 가드 + 업로드 전 캐시 최신화(앱 새로고침/재설치) 운영수칙을 **함께** 둔다.
- staging 검증(sim_parse: 정상 PASS + 손상 4주 PDF 차단) → 사용자 staging 도메인 확인 → prod sync.

### 4-2. 토요일 파서 재검증
네 핸드오프 §4-1 "line 341 이 토요일 버림"은 **prod 실데이터와 모순**이다 —
토요일 행이 여러 주에 `pdf_key` 있는 업로드 산출로 정상 존재(7/25 동태매운탕·7/11·7/04·6/27·6/20 …).
즉 **현재 업로드 경로는 토요일을 저장하고 있다.** sim_parse 에 **토 포함 케이스**로 재검증 요청.
(단 4/11 토요일은 옛 파서 시절이라 누락됐음 — 옛/신 파서 차이일 수 있다.)

### 4-3. 파서 출력 형식 규명
`' / '` → 개행 전환이 언제/어디서(프론트 vs 백엔드)인지, 옛 `' / '` 형식이 밀림과 인과인지.
